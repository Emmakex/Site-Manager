# Site Manager MCP bridge

Scoped MCP operator bridge for one Site Manager connection.

The bridge reuses the connection created in WordPress under **Site Manager > Connection**. There is no second WordPress credential or entitlement model. The same bearer token protects the inbound `/mcp` endpoint and authenticates outbound calls to Site Manager REST.

WordPress Site Manager remains the source of truth for granted scopes, capability ownership, provider selection, plan freshness, confirmation, verification and rollback. The bridge exposes only fixed high-level tools and never constructs arbitrary WordPress REST routes.

## Tools

Tool visibility is loaded from the current WordPress connection scopes when the bridge starts.

Read scopes:

- `site_read` — reads only `discovery` and `capabilities`; requires `site.read`.
- `site_diagnostics` — reads only `diagnostics`; requires `site.diagnostics`.

Governed content writes, available only with `content.write`:

- `content_update_plan`
- `content_update_apply`
- `content_update_rollback`

Governed navigation writes, available only with `navigation.write`:

- `navigation_update_plan`
- `navigation_update_apply`
- `navigation_update_rollback`

Navigation plans accept only the native providers already understood by Site Manager: `wordpress-classic-menu` and `wordpress-block-navigation`. WordPress validates provider/target ownership and provider-specific fields before a plan is created.

Governed SEO writes, available only with `seo.write`:

- `seo_update_plan`
- `seo_update_apply`
- `seo_update_rollback`

SEO plans are provider-aware. The MCP tool accepts the stable semantic fields `title`, `description`, `canonical` and `indexability`, but WordPress resolves the active SEO authority and rejects any field that the current provider does not govern. Supported provider adapters remain Site Manager's existing SEO/GEO Theme, Yoast SEO, Rank Math and AIOSEO adapters. The bridge does not choose a provider and does not write provider storage directly.

Every write follows `plan -> explicit confirmation -> apply -> verify`, with rollback available while retained evidence remains valid. Unknown, expired, stale or scope-mismatched plans fail closed.

## Configuration

Required runtime variables:

- `SITE_MANAGER_REST_BASE` — REST base displayed by the WordPress connection page, ending at `site-manager/v1/`.
- `SITE_MANAGER_CONNECTION_ID` — non-secret `smc_...` identifier displayed by WordPress.
- `SITE_MANAGER_TOKEN` — one-time bearer secret generated by WordPress. Never commit or paste the real value into ordinary chat messages.

Optional runtime variables:

- `SITE_MANAGER_TIMEOUT_MS` — defaults to `10000`.
- `HOST` — process bind address; Compose pins this to `0.0.0.0` inside the container.
- `PORT` — process port; Compose pins this to `8787` inside the container.
- `SITE_MANAGER_MCP_BIND_PORT` — host-side loopback port used by `compose.yaml`; defaults to `8787`.

Non-local REST targets must use HTTPS. Redirect following is disabled so the bearer cannot be forwarded to another origin.

## Persistent service (recommended)

The production single-site runtime is `compose.yaml`. It is deliberately loopback-only by default and is hardened with a read-only filesystem, dropped Linux capabilities, `no-new-privileges`, a small `/tmp` tmpfs, a PID limit and an HTTP healthcheck.

The service uses `restart: unless-stopped`, so it stays running after the operator disconnects from SSH and is restarted by Docker after daemon/host restarts. This does not make the MCP port public: `127.0.0.1:<port>` is the default host binding.

On the server, from this directory:

```bash
sh scripts/configure-persistent.sh
```

The configurator asks for the REST base and connection id, reads the bearer token with terminal echo disabled, writes `.env` with mode `0600`, validates Compose without printing the resolved secret, builds the image and starts it detached.

Useful operations:

```bash
# Current service/health state
docker compose -f compose.yaml ps

# Bounded logs
docker compose -f compose.yaml logs --tail=100 site-manager-mcp

# Rebuild after updating the repository
docker compose -f compose.yaml up -d --build

# Stop without deleting the local secret file
docker compose -f compose.yaml stop

# Start again
docker compose -f compose.yaml start

# Remove the container/network; .env remains local
docker compose -f compose.yaml down
```

Do not run `docker compose config` without `--quiet` on a machine holding a real `.env`, because resolved configuration output may contain environment values. `.env` is ignored by Git and must remain operator-owned.

### Persistent presence in WordPress

The bridge makes authenticated REST calls to Site Manager while it polls the remote acceptance job at low frequency. WordPress records only bounded MCP client metadata and recent presence, never the plaintext bearer. **Site Manager > Connection** therefore changes to `MCP connected` after the persistent bridge authenticates and naturally ages back to not connected if the service is stopped.

Scope visibility is loaded when the bridge process starts. After changing scopes in WordPress, restart the service so MCP tool visibility matches the new grant:

```bash
docker compose -f compose.yaml restart site-manager-mcp
```

### Public ingress

The persistent Compose definition intentionally does **not** expose MCP publicly. If remote MCP clients need inbound access, place an authenticated TLS reverse proxy in front of the loopback listener as a separate deployment decision. Do not change the Compose bind to `0.0.0.0` merely for convenience.

## One-off container development

For local development only:

```bash
docker build -t site-manager-mcp:0.5.0 .
docker run --rm -p 127.0.0.1:8787:8787 \
  -e SITE_MANAGER_REST_BASE='https://example.com/wp-json/site-manager/v1/' \
  -e SITE_MANAGER_CONNECTION_ID='smc_...' \
  -e SITE_MANAGER_TOKEN="$SITE_MANAGER_TOKEN" \
  site-manager-mcp:0.5.0
```

Prefer the persistent configurator for real installations so the token is not placed in command history.

## HTTP surface

- `GET /healthz` — public non-secret process health and bridge mode.
- `/mcp` — MCP transport; requires `Authorization: Bearer <the same Site Manager connection token>`.
- every other path returns 404.

## Accepted governance path

The live EMMake acceptance established the complete product path for content, navigation and SEO through the WordPress-triggered MCP Acceptance Center. Each write uses Site Manager's existing plan/apply/verify/rollback contracts and the remote acceptance runner executes one bounded phase at a time with concurrency 1.

The bridge never auto-grants a write scope, infers SEO ownership or bypasses Site Manager's provider contracts.
